# Transaction Search & Explorer Architecture

## Overview
The Transaction Explorer provides financial analysts and risk operations teams with a low-latency, search-first interface for auditing, investigating, and tracing financial transactions through the real-time detection pipeline.

---

## 1. Core Endpoints

### 1.1 List & Filter Transactions
* **Endpoint:** `GET /api/v1/transactions`
* **Query Parameters:**
  * `search` (string): Debounced prefix/exact search across indexed identifiers (`transaction_id`, `user_id`, `merchant_id`, `device_id`).
  * `risk_level` (string, enum): `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
  * `status` (string, enum): `PENDING`, `COMPLETED`, `FAILED`, `DECLINED`, `REVERSED`, `CANCELLED`.
  * `min_amount` / `max_amount` (float): Numeric threshold filters.
  * `min_risk_score` / `max_risk_score` (float: 0.0 – 100.0): Composite risk score range.
  * `start_date` / `end_date` (ISO-8601 string): Date bounds with interactive query limit (capped at 90 days).
  * `currency` (string, 3-letter ISO code): E.g., `USD`, `EUR`, `GBP`.
  * `transaction_type` (string, enum): `PURCHASE`, `TRANSFER`, `WITHDRAWAL`, `DEPOSIT`, `PAYMENT`, `REFUND`.
  * `sort_by` (string, allowlisted): `timestamp`, `amount`, `risk_score`, `status`, `created_at`.
  * `sort_order` (string): `asc` or `desc` (default: `desc`).
  * `page` (int, default: 1): 1-indexed pagination.
  * `page_size` (int, default: 25, options: 25, 50, 100, max: 100).

### 1.2 Full Investigation Telemetry
* **Endpoint:** `GET /api/v1/transactions/{transaction_id}/investigate`
* **Returns:**
  * `transaction`: Core financial parameters, masked card PAN, user metadata, geolocation, and device fingerprints.
  * `risk`: Composite risk score (0–100), risk band, score version, and structured risk explanation signals.
  * `rules`: Comprehensive rule executions with triggered status, severity, score contribution, reason, and structured evidence.
  * `ml_prediction`: Isolation forest anomaly score, binary anomaly flag, threshold, model version, and contextual indicators.
  * `features`: Feature store snapshot containing velocity counters, amount deviation ratios, and categorical flags.
  * `alerts`: Associated security alerts generated by the pipeline.

## 2. Search & Filter Architecture

```
User Query Input (Debounced 350ms)
       │
       ▼
Validated Query Params (Pydantic / FastAPI)
       │
       ├── Exact Lookup (Index hit: transaction_id, user_id, merchant_id, device_id)
       ├── Date Range Validation (Start <= End, Max 90-day interactive span)
       ├── Allowlisted Sorting (SQLAlchemy expression builder)
       └── Server-Side Offset Pagination (Limit/Offset)
       │
       ▼
Optimized Query Execution (PostgreSQL / SQLite Index Scans)
       │
       ▼
Structured Response Envelope (items, total, page, page_size, total_pages)
```

## 3. Query Optimization & Indexing

The transaction database utilizes targeted composite and single-column B-tree indexes:
* `ix_transactions_timestamp`: Fast time-series sorting and range bounding.
* `ix_transactions_user_id`: Per-user transaction history and aggregation.
* `ix_transactions_merchant_id`: Merchant velocity filtering.
* `ix_transactions_device_id`: Device fingerprint tracking.
* `ix_transactions_risk_level`: Filter by risk band.
* `ix_transactions_status`: Filter by settlement/authorization status.

## 4. Security & Privacy

1. **Authentication & RBAC:**
   * Requires valid JWT Bearer token with permission `read:transactions`.
   * Enforced via FastAPI dependency injection (`require_permissions(["read:transactions"])`).
2. **PCI-DSS Compliance:**
   * Full card numbers and sensitive auth tokens are never stored or returned. Card PAN is masked (e.g., `•••• 4821`).
3. **Safe Query Formulation:**
   * Raw SQL string concatenation is prohibited; all queries utilize SQLAlchemy declarative ORM filters.
   * `sort_by` fields are strictly verified against an allowed set (`ALLOWED_SORT_FIELDS`).
